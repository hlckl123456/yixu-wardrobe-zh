# 衣橱整理与 AI 协作流程

这份指南整理了从衣物照片到已审核搭配的工作方法，供使用者和协作的 AI agent 参考。它不包含任何人的照片、衣物清单、尺码、购买记录或个人偏好。

网站负责浏览，照片处理、搭配构思和数据维护在外部工具与本机维护命令中完成。下文的检查步骤需要实际执行，不代表网站已经内置自动处理或自动审核。

## 先确认当前项目

开始前阅读 `AGENTS.md`、[维护说明](MAINTENANCE.md)和[架构说明](ARCHITECTURE.md)。确认项目根目录、数据目录、本机端口及当前数据库。使用支持 SQLite 的 Node.js 24 或更新版本；遇到 `node:sqlite` 缺失时先核对 Node 版本。

为另一个人新建衣橱时，从源码和空数据库开始。可以复用界面和处理方法，衣物、尺码、喜好、购物决定及图片重建授权则要单独确认。不要把旧衣橱的数据库或偏好当作新衣橱的初始内容。

服务只监听本机回环地址。端口权限错误不代表数据库损坏，不要为了绕过错误改成公网或局域网监听。测试使用临时目录与数据库。

## 收到一批照片后

1. 逐张查看原图，确认要整理的单品和所有权。同一张照片里的其他颜色、背景商品或模特内搭，不自动算作已有衣服。只针对真正不明确的地方提问。
2. 先确认原图保留方式。可以使用 `private-data/inbox/originals/` 保存原件、`private-data/staging/` 暂存处理图；这两个目录是组织建议，需要自行创建。无论采用哪种保留方式，都不要移动或删除用户项目外的源文件。
3. 记录来源和哈希，并与当前库存查重。同一件衣服的新照片应沿用原身份；同一张图里的不同单品用稳定的 `sourceItemKey` 区分，不能伪造哈希绕过去重。
4. 分开保留原图和处理版本。核对颜色、纹理、商标、图案、领口、袖型、开合、下摆、长度和鞋的前后结构。
5. 区分去背景与生成式重建。补全原图看不见的部分需要明确授权，并记录 `processingMethod` 和审核说明。不得仅因图片看起来更完整就悄悄换款、换色或发明细节。
6. 对处理结果逐张做视觉检查。补全、偏色、透明边缘、印字变化或结构不确定时，提供原图与处理图对比。工具返回成功不等于图片已经合格。
7. 用户确认的图片保留准确字节。按[录入说明](MAINTENANCE.md#录入衣物)准备资料并运行 `scripts/intake.mjs`；核对数据库、登记图片、实际文件和页面后，再报告保存成功。
8. 每批给简短回执，列出数量、稳定编号、名称或缩略图、重复项和仍需确认的地方。

## 容易识别错的细节

- 假两件可能是一件不可拆分的衣物，不能仅凭领口或下摆的视觉层次录成两件。
- 鞋要区分完整后跟、露跟、厚底和高跟。“有跟”可能指后跟围完整；结合侧面和后面照片确认，不靠一个词决定鞋型。
- 衣架品牌不是衣物品牌证据；商品截图也不能证明全部颜色都已购买。
- 图片不能验证精确尺寸、面料成分、品牌真伪、填充物、保暖等级或本人合身程度。未知字段保持未知。
- AI 整理图和搭配图应准确标为示意，不能当作本人试穿或细节完全一致的证据。

用户纠正单品结构或颜色时，先核对当前记录，再沿真实关联检查受影响的正式搭配和候选页。只修正相关内容，保留旧版本及其他已经认可的画面。

## 制作和审核搭配候选

1. 从当前在用的真实衣物及最新审核图开始。已有、待购、参考、已移除和准备丢弃的单品要分清。
2. 生成时使用准确的单品参考图，记录真实 ID、图片版本及穿法。默认不发明衣物、不偷偷换色，也不假设某种基础款已经拥有。需要使用假设时，先确认授权并明确披露，不能录成真实库存。
3. 一起检查上下装正式程度、廓形、宽窄、长度、色彩、鞋型和层次。某条裤子在某套里不合适，并不意味着用户讨厌这件单品或全部同类裤装。
4. 保留用户明确喜欢的部分，再针对颜色、版型或比例提出替换。个人审美以当前使用者的反馈为准。
5. 批量候选应包含真正不同的衣服组合。只换鞋、配饰、姿势或穿法，不应冒充大量新搭配。可用主体上装与下装组合检查本批及历史重复。
6. 让完整衣服和双鞋清楚可见，逐图核对领口、图案、裤腰、下摆、鞋跟和穿法，并记录图像不确定处。
7. 可以用稳定的 `HX` 候选编号和共享评审页供用户选择。`dist/reviews/candidate-review.js` 可作实现参考；私有页面和媒体仍须遵循登记机制。

候选页不会自动成为「我的搭配」。用户明确选定后，使用已审核的准确图片字节，通过 `scripts/save-owned-outfit.mjs` 正式保存；不要在保存时重新生成图片。按用户选择顺序保存，重复编号去重，语音歧义结合当前候选范围核对。

“暂缓”“再看看”和未选中不算同意。用户明确要求移除搭配时，按准确编号执行；后续修正版仍是新的候选，等再次选择。不要擅自重排已有记录或恢复此前删除的搭配。

## 理解现有网站

- 主入口为「我的搭配」「随心配」「我的衣橱」，以桌面浏览和清楚的衣物图片为主。
- 「我的搭配」保留保存顺序，季节和风格只筛选当前显示。
- 「随心配」从符合季节和心情的已保存搭配中随机取最多四套，首次也随机，同一轮优先展示没看过的搭配。它不会实时调用模型，也不会在无匹配时自动放宽条件。
- 调色盘切换四种页面配色。衣橱概览和准备丢弃是衣橱内的次级功能。
- 「未用到」「仅用在 1–2 套」统计正式搭配引用次数，不是穿着次数，也不构成丢弃建议。

## 维护数据时

稳定别名用于和用户沟通，内部 ID 用于数据关联。`WT`、`SY`、`KZ`、`XZ`、`PS` 和 `DP` 分别用于外套、上装、下装、鞋、配饰和正式搭配。操作前从当前数据库解析准确编号，不凭名称或页面位置猜测；删除后编号也不复用。

SQLite 是唯一可写记录。正式搭配使用的衣物以 `outfit_items` 为准，来源以 `outfit_sources` 为准。不要从标题或页面数组推断关系，也不要另建可写 JSON 清单作为第二份库存。

常规写入通过本机服务完成。修改前核对准确记录和影响范围；取消购买、准备丢弃、明确删除是不同操作。`pending-discard` 保留所有权与历史，但不能加入新的普通搭配。

图片用新路径保存新版本，登记哈希和来源，不能原地覆盖已审核文件。图片登记、保存记录和完整性检查是不同步骤，需要一起完成。只有图片文件存在不代表数据录入成功。

完整备份应包含一致的数据库和已登记图片。先在新目录验证恢复，再切换；数据库快照不能代替完整图片备份。源码发布使用明确的文件允许清单，不包含私人照片、数据库、回执或旧 Git 历史。

## 交接给一个新 chat

新 chat 不会自动继承旧 chat 的全部历史。把通用方法、当前环境和使用者的私有记录分开维护。较新的明确纠正优先于旧信息；个人记录放在私有数据目录或本项目 `documents.preferences` 的 `workflowHistory` 中，通过服务命令维护。

下面的模板适合写在私有交接文件中。填写后的本机路径、个人资料和回执不要提交到公开仓库。

```text
项目目录：<project-root>
数据目录：<private-data-directory>
本机地址：<loopback-origin>
当前状态：<已完成、待审核、失败和待确认的批次>
先阅读：AGENTS.md、维护文档、本项目私有工作记录
已确认授权：<图片处理范围、重建授权、选择与删除决定>
当前偏好：<本人的明确反馈，附来源>
待继续：<下一批照片或候选，以及验收标准>
```

交接完成后，让接手的 agent 实际阅读规则，核对项目、数据库和服务标识，再从未完成的步骤继续。不要重复建库、重新生成已认可的图片或重新分配旧编号。
